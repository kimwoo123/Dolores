# 계획 기반 작업 워크플로

기능 추가/변경 작업은 **계획 문서 먼저, 그다음 테스트, 그다음 구현** 순서로 진행합니다.
오타·문서·리네임 등 사소한 작업에는 적용하지 않습니다.

## 흐름

```
1. 계획 문서 작성 (.plan/<task>.md) → 계획 + 테스트 시나리오 포함
2. 모호한 부분 질문 → 계획/시나리오가 확정될 때까지 사용자에게 확인
3. 테스트 시나리오 → 테스트 코드 작성
4. 테스트 코드 → 기능 구현 (테스트 통과가 완료 기준)
5. 완료 후 계획 문서에 완료 표시
```

## 1. 계획 문서 — `.plan/`

- 위치: 프로젝트 루트의 `.plan/` (로컬 전용, `.gitignore` 처리 — 커밋하지 않음)
- 파일명: `<task>.md` (kebab-case, 작업 내용을 알 수 있게)
- 문서는 최소 두 부분을 포함:
  - **계획**: 무엇을, 왜, 어떤 순서로
  - **테스트 시나리오**: 기능의 동작을 GIVEN/WHEN/THEN 으로 기술 (→ [testing.md](testing.md) 의 BDD 스타일과 동일)

### 문서 템플릿

```markdown
# <작업 제목>

상태: 진행 중   <!-- 완료 시 "완료" 로 갱신 -->

## 계획

- 배경/목표:
- 단계:
  1. ...
  2. ...

## 테스트 시나리오

### 시나리오 1: <이름>
- GIVEN: ...
- WHEN: ...
- THEN: ...

### 시나리오 2: <이름>
- GIVEN: ...
- WHEN: ...
- THEN: ...
```

## 2. 모호함은 먼저 질문

계획과 테스트 시나리오에 모호하거나 해석이 갈리는 부분이 있으면 **구현을 시작하기 전에** 사용자에게 질문합니다.
(전역 지침 "Think Before Coding" 과 동일 — 추측해서 진행하지 않음)

확인할 대표 항목:
- 입력/출력의 경계값·예외 케이스가 시나리오에 빠져 있지 않은가
- "성공"의 기준이 검증 가능한가 (모호하면 시나리오로 구체화)
- 여러 해석이 가능한 요구사항이 있는가

## 3. 테스트 시나리오 → 테스트 코드

- 문서의 각 시나리오를 테스트 함수로 옮깁니다. 테스트 docstring 은 시나리오의 GIVEN/WHEN/THEN 을 그대로 사용.
- 테스트 작성 규칙은 [testing.md](testing.md) 를 따름 (factory, fixture, 인덱스 격리 등).

## 4. 테스트 코드 → 구현

- 작성한 테스트가 통과하도록 기능을 구현합니다. **테스트 통과가 완료 기준**.
- 시나리오에 없던 동작을 임의로 추가하지 않음 (전역 지침 "Simplicity First").

## 5. 완료 표시

- 테스트 통과 + 구현 완료 후 계획 문서 상단의 `상태:` 를 `완료` 로 갱신합니다.
- 문서는 삭제하지 않고 `.plan/` 에 남겨 둡니다 (로컬 작업 이력).
